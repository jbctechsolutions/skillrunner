### Feature: MCP Provider Integration

**Linear:** JBC-940 (5 pts)
**Priority:** P0 — critical path blocker for all MCP workflows

**Problem:** Skills can see MCP tools via the registry, but no provider ever receives them. Tool calling is dead code.

**Solution:** Thread MCP tools through the full execution loop:
1. Phase executor fetches tool definitions from `MCPToolRegistryPort`
2. Convert to provider format (existing `tool_converter.go`)
3. Pass in `CompletionRequest.Tools`
4. Handle `tool_use` blocks in the response
5. Execute tool via `MCPToolRegistryPort`
6. Feed tool result back to provider for continuation

**Key files:**
- `internal/application/workflow/phase_executor.go`
- `internal/application/workflow/streaming_phase_executor.go`
- `internal/adapters/provider/anthropic/client.go`
- `internal/adapters/provider/anthropic/streaming.go`

**Acceptance criteria:**
- [ ] Executor fetches tools from MCP registry before phase execution
- [ ] Tools passed in `CompletionRequest.Tools`
- [ ] Anthropic adapter parses and handles `tool_use` response blocks
- [ ] Tool execution via `MCPToolRegistryPort`
- [ ] Tool results fed back to provider for continuation
- [ ] Unit tests + integration test with real API
- [ ] Works with existing Linear, Filesystem, Git MCP servers

**Success metric:** `sr run linear-skill "List my open issues and count them"` calls `linear__list_issues` and returns a count.

### Feature: Skills Declare Tool Requirements

**Linear:** JBC-941 (2 pts)
**Priority:** P0

**Problem:** No way to declare which MCP tools a skill needs, making validation and permission prompts impossible.

**Solution:** Add `tools` and `allow_tools` fields to skill YAML schema.

```yaml
id: linear-plan-generator
tools:
  - mcp__linear__get_issue
  - mcp__linear__list_issues
  - mcp__filesystem__write_file
phases:
  - id: generate
    allow_tools: true
    prompt_template: |
      Generate implementation plan for: {{.input}}
```

**Key files:**
- `internal/domain/skill/skill.go` — add `Tools []string`
- `internal/domain/skill/phase.go` — add `AllowTools bool`
- `internal/infrastructure/skills/loader.go` — parse YAML fields

**Acceptance criteria:**

- [ ] YAML parser reads both fields
- [ ] Validation: tool names must match `mcp__server__tool` format

## v1.3 — Make It Cheap

### Feature: Adaptive Complexity Analysis

**Priority:** P0
**Estimated value:** Biggest cost lever — routes 60–70% of tasks to cheap models.

**Problem:** Every task goes through the routing profile set by the skill YAML. Simple requests pay premium prices.

**Solution:** Analyze task complexity before model selection. Map score to routing profile automatically. `--profile` flag overrides.

```
Complexity score: 0.35 → routed to cheap (llama3.2:3b)
Complexity score: 0.92 → routed to premium (claude-sonnet-4.5)
```

**Complexity signals:**
- Request length (token count)
- Technical keyword density ("distributed", "async", "security", "race condition")
- Code volume
- Historical success rate for this skill + complexity range

**Key files:**
- `internal/domain/complexity/` (new) — `analyzer.go`, `signals.go`
- `internal/infrastructure/complexity/analyzer.go` (new)
- `internal/application/workflow/executor.go` — integrate analyzer before routing

**Acceptance criteria:**
- [ ] Scores 0.0 (trivial) → 1.0 (expert-level)
- [ ] Mapping: 0–0.4 = cheap, 0.4–0.7 = balanced, 0.7+ = premium
- [ ] `--profile` flag bypasses complexity analysis
- [ ] Metrics track complexity scores vs. actual outcomes
- [ ] Unit tests with varied request types

### Feature: Enhanced Response Caching (Semantic)

**Priority:** P0
**Estimated value:** 20–30% additional cache hit rate.

**Problem:** Exact-match caching (SHA256) misses semantically similar requests with different phrasing.

**Solution:** Embedding-based similarity cache. Requests within 0.90 cosine distance = cache hit.

```bash
sr run doc-gen "Explain what auth.go does"   # Miss → full execution
sr run doc-gen "Describe the auth.go file"   # Hit → cached response
```

**Key files:**
- `internal/adapters/cache/semantic_cache.go` (new)
- `internal/infrastructure/embeddings/` (new) — embedding generation
- `internal/application/workflow/executor.go` — check semantic cache before exact cache

**Acceptance criteria:**
- [ ] Embedding-based similarity check (cosine distance)
- [ ] Threshold: ≥0.90 similarity = cache hit
- [ ] Graceful fallback to exact match when embedding service unavailable
- [ ] Config: `cache.semantic_similarity_enabled` (default: false)
- [ ] Metrics: semantic hit count vs. exact hit count

### Feature: Context Compression

**Priority:** P1
**Estimated value:** 30–50% token reduction on verbose inputs.

**Problem:** Large file contexts, verbose logs, and repeated content inflate token counts unnecessarily.

**Solution:** Pre-processing pipeline to compress context before provider calls. Strategy varies by routing profile.

**Strategies:**
- Whitespace normalization
- Deduplication of repeated blocks
- Summary substitution for verbose logs
- Comment stripping (when safe / opt-in)

**Acceptance criteria:**
- [ ] Multiple compression strategies implemented
- [ ] Config: `context.compression_enabled`
- [ ] Aggressive mode (>70% target reduction) applied on `cheap` profile
- [ ] Conservative mode (<30% target) applied on `premium` profile
- [ ] Semantic meaning preserved (compression should not change answers)
- [ ] Compression ratio tracked in metrics

### Feature: Ollama Model Optimization

**Priority:** P1

**Problem:** Ollama model selection is generic. Some models are dramatically better at specific tasks (e.g., `qwen2.5` for code vs. `llama3.2` for docs).

**Solution:** Task-specific model hints per skill, configurable in `~/.skillrunner/config.yaml`.

```yaml
routing:
  skill_model_hints:
    code-review:
      cheap: qwen2.5:14b
      balanced: qwen2.5-coder:32b
    doc-gen:
      cheap: llama3.2:3b
```

**Acceptance criteria:**
- [ ] `routing.skill_model_hints` config field
- [ ] Ollama provider reads hints before default model selection
- [ ] Automatic fallback if hinted model not available
- [ ] `sr models recommend` command shows suggestions per skill

## v1.4 — Make It Smart

**Theme:** Learn from execution, operate safely, handle failures gracefully.
**Goal:** Higher quality outputs, zero code disasters, resilient workflows.
**Timeline:** 4–5 weeks, ~15 points
**Depends on:** v1.3 complete

---

### Feature: Outcome Tracking & Learning

**Priority:** P0
**Estimated value:** Routing profile self-optimizes over time.

**Problem:** Every run starts from scratch. There's no memory of which model worked well for which skill+task type.

**Solution:** SQLite-backed outcome history. Track success/failure + optional quality scores per skill + routing profile combination. Surface recommendations.

```bash
sr outcomes show code-review
# → Phase 'report' using haiku: 89% success, 0.8 avg retries → suggest upgrade to sonnet
```

**Key files:**
- `internal/domain/outcome/` (new) — outcome aggregate
- `internal/infrastructure/storage/outcome_repository.go` (new)
- `internal/application/workflow/executor.go` — record outcome after each phase

**Acceptance criteria:**
- [ ] SQLite table for outcomes: skill, phase, profile, model, success, quality_score, timestamp
- [ ] Outcomes recorded after every phase execution
- [ ] `sr outcomes show <skill>` displays history + trends
- [ ] Automatic routing profile suggestions based on outcome history
- [ ] `sr outcomes reset <skill>` clears history for a skill

---

### Feature: Confidence Monitoring & Auto-Escalation

**Priority:** P0

**Problem:** Cheap models sometimes produce low-confidence answers. Without detection, these propagate downstream as if they were high-quality outputs.

**Solution:** Parse confidence markers from LLM responses. If below threshold, retry with the next-tier model automatically.

**Acceptance criteria:**
- [ ] Confidence parser identifies uncertainty markers in LLM output ("I'm not sure", "approximately", hedged language)
- [ ] Configurable threshold per routing profile: `routing.confidence_threshold.cheap: 0.7`
- [ ] Automatic retry with next-tier model when confidence is below threshold
- [ ] Escalation is logged and counted in metrics
- [ ] `--skip-escalation` flag to disable for speed

---

### Feature: Git Worktree Isolation

**Priority:** P1

**Problem:** Code modification skills (refactor, lint-fix, test-fix) write directly to the working tree. A bad LLM output corrupts the repo with no easy undo.

**Solution:** `--isolate` flag creates a git worktree for the execution. After completion, show a diff and offer merge/discard.

```bash
sr run refactor "Extract auth module" --isolate
# Creates: ~/.skillrunner/worktrees/refactor-2026-02-26-abc123/
# After completion:
# Show diff → merge into working tree or discard
```

**Key files:**
- `internal/domain/isolation/` (new)
- `internal/infrastructure/git/worktree.go` (new)
- `internal/application/workflow/executor.go` — isolation mode

**Acceptance criteria:**
- [ ] `--isolate` flag on `sr run`
- [ ] Worktree created at `~/.skillrunner/worktrees/<skill>-<date>-<hash>/`
- [ ] Post-execution: show unified diff, prompt merge or discard
- [ ] Merge applies changes to working tree; discard deletes worktree
- [ ] Stale worktrees (>7 days) auto-cleaned

---

### Feature: Session Continuity (Resume)

**Priority:** P1

**Problem:** Interrupted multi-phase workflows require full re-execution from scratch. Phases that completed successfully are re-run, wasting time and money.

**Solution:** `sr resume` picks up from the last successful phase checkpoint.

```bash
sr run complex-pipeline "..."   # interrupted at phase 3 of 5
sr resume                       # resumes from phase 3
sr resume --list                # show resumable sessions
```

**Acceptance criteria:**
- [ ] Checkpoint stored in SQLite after each successful phase
- [ ] `sr resume` detects and offers resumable sessions
- [ ] `sr resume --list` shows sessions with skill name, timestamp, last phase
- [ ] Session TTL: 24 hours (configurable via `session.resume_ttl`)
- [ ] Sessions older than TTL are not shown

---

### Feature: Post-Completion Review Phases

**Priority:** P2

**Problem:** Code generation skills produce output that may have subtle errors not caught during generation. No automatic quality gate before presenting to the user.

**Solution:** Skills can declare `post_completion_review: true` on phases. A review phase runs automatically and can reject + retry the generation.

**Acceptance criteria:**
- [ ] `Phase` struct has `PostCompletionReview bool` field
- [ ] Review phase executes after generation phase completes
- [ ] If review rejects, generation phase retries (max 2 retries)
- [ ] `--skip-review` flag for speed
- [ ] Review outcome tracked in outcome history

---

### Feature: Universal Agent Format Export

**Priority:** P2

**Problem:** Workflow results are displayed in the terminal but can't be consumed by other AI tools (Claude Code, Cursor, Aider) for continuation.

**Solution:** `--export-format` flag on `run`/`ask` exports workflow results in a portable format.

```bash
sr run code-review "..." --export-format=claude-code > review.md
```

**Acceptance criteria:**
- [ ] `--export-format` flag: `claude-code`, `aider`, `cursor`, `json`
- [ ] Export includes: messages, files, suggestions, context
- [ ] JSON format is the canonical interchange format
- [ ] Other formats are thin wrappers around JSON
